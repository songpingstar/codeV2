# Figma 原型到设计文档生成指南

本 Skill 专注于从 Figma 原型设计生成完整的设计文档，为后续代码开发提供清晰的技术规范和设计依据。

## 适用场景

当您需要：
- 从 Figma 原型开始准备系统开发所需的设计文档
- 了解从 0 到 1 开发系统需要准备哪些设计文档
- 进行系统架构设计、数据库设计和 API 接口设计
- 制定权限模型和安全规范
- 为开发团队提供完整的技术设计文档

## 开发阶段总览

### 阶段 1：原型 → 产品定义

**目标**：将 Figma 原型转化为产品需求文档

**产出文档**：
- `doc/01_PRD.md` - 产品需求文档
- `doc/02_feature_breakdown.xlsx` - 功能点拆分表

**关键任务**：
1. 分析 Figma 原型页面结构
2. 按模块拆分功能需求：
   - 仪表盘
   - 脚本管理
   - 任务执行
   - 调度管理
   - 节点管理
   - 系统设置
3. 每个模块包含：
   - 功能描述
   - 规则说明
   - 权限说明
   - 验收标准
4. 将功能拆分为可开发颗粒度的功能点，给每个功能点增加 FeatureID

### 阶段 2：产品 → 架构设计

**目标**：设计系统总体架构

**产出文档**：
- `doc/03_architecture.md` - 架构设计文档

**关键任务**：
1. 设计分布式系统架构
2. 确保架构满足约束条件：
   - 管理节点不直接执行脚本
   - 采用 Agent 执行架构
   - 支持异步任务
   - 支持水平扩展
3. 输出：
   - 架构说明
   - 模块边界
   - 执行流程图
   - 技术栈建议

### 阶段 3：架构 → 数据 & API

**目标**：设计数据库模型和 API 接口

**产出文档**：
- `doc/04_database_design.md` - 数据库设计文档
- `doc/database/schema.sql` - 数据库表结构 SQL
- `doc/api/07_api_mapping_table.md` - API 接口映射表
- `doc/05_openapi.yaml` - OpenAPI 3.0 规范

**关键任务**：
1. 设计 SQLite 数据库模型：
   - 表结构 SQL
   - 主键、外键设计
   - 关键索引
   - 不可变执行记录设计
   - SQLite 特性优化（WAL 模式、事务处理）
2. 生成 API 接口映射表：
   - 按模块输出接口（Script、Node、Task、Execution、Schedule、Auth）
   - 在接口映射表中增加 FeatureID 列，与功能点拆分表中的 FeatureID 对应
   - 定义每个接口的 URL、HTTP 方法、请求参数、响应结构
   - 标注权限角色和分页/批量操作
   - 遵循 RESTful 规范和统一设计规范
   - 生成接口数量统计和模块汇总

   **接口字段规范**：
   - 模块名称、页面名称、功能点名称
   - URL（统一使用 /api/v1/ 前缀）
   - HTTP 方法（GET/POST/PUT/DELETE）
   - 请求参数：字段名、类型、是否必填、默认值、描述
   - 响应结构：code、message、data 及内部字段明细
   - 权限角色：admin / ops / readonly
   - 是否分页、是否批量操作、备注说明

   **设计规范**：
   - RESTful 规范，URL 语义清晰
   - 分页接口统一使用 page、size 参数
   - 批量接口使用 /batch 后缀
   - 版本号统一为 v1
   - 状态字段统一：pending、running、success、failed、timeout、disabled

   **输出格式**：
   - Markdown 表格（可直接导入 Excel）
   - 每个模块单独一个表
   - 字段列完整清晰，不允许省略字段
   - 生成接口数量统计和模块接口数量汇总
3. 生成 OpenAPI 3.0 规范：
   - REST 风格 API
   - 明确错误码
   - 每个接口标注权限要求

### 阶段 4：安全与权限

**目标**：设计 RBAC 权限模型

**产出文档**：
- `doc/06_rbac_design.md` - RBAC 权限设计文档

**关键任务**：
1. 定义角色：admin、ops、readonly
2. 设计权限点列表
3. 创建 API → 权限映射
4. 数据库设计
5. FastAPI 中间件示例


## 使用指南

### 启动条件

当满足以下任一条件时，应调用本 Skill：
1. 用户拿到 Figma 原型设计，准备生成设计文档
2. 用户询问需要准备哪些设计文档来进行工程化控制
3. 用户需要从原型到设计文档的完整流程指导
4. 项目进入设计阶段，需要生成技术规范文档

### 执行步骤

1. **需求确认**：确认 Figma 原型是否已就绪，理解系统功能范围
2. **阶段选择**：根据项目需求，选择需要生成的文档阶段
3. **文档生成**：按照阶段要求生成相应的设计文档
4. **文档评审**：组织评审会议，确认设计文档的完整性和准确性
5. **文档交付**：将最终确认的设计文档交付给开发团队

### 注意事项

- 所有设计文档应存放在 `doc/` 目录下，按模块分类整理
- 文档应保持与 Figma 原型的一致性
- 当有新的功能模块或需求时，应及时更新所有相关设计文档
- 每个阶段完成后，应进行评审和确认
- 设计文档应具备可执行性，能够直接指导代码开发
- 保持设计文档的版本控制和更新记录

## 质量标准

### 文档质量要求

- 所有设计文档必须清晰、完整、可执行
- 文档内容应与 Figma 原型保持一致
- 每个文档应包含明确的目标和范围
- 技术设计应具备可实现性和可维护性
- 文档应经过评审和确认后才能交付

### 设计完整性要求

- PRD 文档应覆盖所有功能模块和用户场景
- 架构设计应明确模块边界和技术选型
- 数据库设计应包含完整的表结构、索引和约束
- API 文档应包含所有接口的详细定义
- 权限设计应覆盖所有角色和权限点

### 文档可读性要求

- 使用清晰的标题结构和层级
- 提供必要的图表和示例
- 使用统一的术语和命名规范
- 包含必要的说明和注释
- 保持文档的简洁性和准确性

## 文档同步规范

### 重要原则

**当PRD或功能拆分表发生任何变更时，必须同步更新所有相关文档，确保文档之间的一致性。**

### 文档依赖关系

```
PRD (01_PRD.md) 
    ↓
功能拆分表 (02_feature_breakdown.md)
    ↓
API映射表 (07_api_mapping_table.md) + OpenAPI规范 (05_openapi.yaml)
    ↓
数据库设计 (schema.sql)
    ↓
架构设计 (03_architecture.md) + RBAC设计 (06_rbac_design.md)
```

### 同步检查清单

当修改PRD或功能拆分表时，必须检查以下文档：

#### 1. 功能拆分表 (02_feature_breakdown.md)
- [ ] 添加新功能行
- [ ] 删除已移除功能行
- [ ] 更新功能描述
- [ ] 重新编号FeatureID（如需要）
- [ ] 更新功能点统计数量

#### 2. API映射表 (07_api_mapping_table.md)
- [ ] 添加新功能的API端点
- [ ] 删除已移除功能的API端点
- [ ] 更新请求参数（添加/删除/修改）
- [ ] 更新响应结构
- [ ] 更新权限要求
- [ ] 确保FeatureID对应关系正确

#### 3. OpenAPI规范 (05_openapi.yaml)
- [ ] 添加新端点定义
- [ ] 删除已移除端点定义
- [ ] 更新参数定义（query/path/body）
- [ ] 更新请求/响应schema
- [ ] 更新示例数据

#### 4. 数据库设计 (schema.sql)
- [ ] 添加新功能所需的表
- [ ] 删除已移除功能的表
- [ ] 修改表结构
- [ ] 添加/删除索引
- [ ] 更新约束和外键关系

#### 5. 架构设计 (03_architecture.md)
- [ ] 添加新组件/模块
- [ ] 更新系统流程图
- [ ] 修改数据流描述
- [ ] 更新技术栈（如需要）

#### 6. RBAC设计 (06_rbac_design.md)
- [ ] 添加新角色（如需要）
- [ ] 添加/删除权限点
- [ ] 更新权限矩阵
- [ ] 更新角色描述

### 常见变更场景

#### 场景1：删除功能
示例：删除"时间范围筛选"功能

1. **PRD**: 删除功能描述
2. **功能拆分表**: 删除功能行，更新统计
3. **API映射表**: 删除相关API端点，移除相关参数
4. **OpenAPI**: 删除端点定义和参数
5. **数据库**: 无需修改（无专用表）
6. **架构**: 无需修改
7. **RBAC**: 无需修改

#### 场景2：添加功能
示例：添加"脚本版本管理"功能

1. **PRD**: 添加功能描述
2. **功能拆分表**: 添加功能行，分配FeatureID，更新统计
3. **API映射表**: 添加API端点（GET/POST/PUT/DELETE）
4. **OpenAPI**: 添加端点定义和schema
5. **数据库**: 添加版本表，添加索引
6. **架构**: 更新组件图和数据流
7. **RBAC**: 添加权限点

#### 场景3：修改功能
示例：修改"脚本分类"为动态可配置

1. **PRD**: 更新功能描述
2. **功能拆分表**: 更新功能描述
3. **API映射表**: 更新API参数和响应
4. **OpenAPI**: 更新schema
5. **数据库**: 修改表结构，添加分类管理表
6. **架构**: 更新模块设计
7. **RBAC**: 更新权限要求

### 质量验证

完成同步后，必须验证：

- [ ] 所有FeatureID唯一且一致
- [ ] 所有功能在API映射表中都有对应端点
- [ ] 所有API端点都在OpenAPI中定义
- [ ] 所有数据结构在数据库中都有对应表
- [ ] 所有权限在RBAC设计中都有定义
- [ ] 没有孤立引用（已删除功能仍被引用）
- [ ] 统计数据准确

### 最佳实践

1. **从源头开始**：PRD和功能拆分表是源头，先修改它们
2. **按依赖顺序更新**：从高层文档到低层文档
3. **保持命名一致**：功能名、API路径、表名应对应
4. **稳定FeatureID**：避免不必要的重新编号
5. **记录变更**：在文档中添加变更说明
6. **交叉验证**：确保文档间没有矛盾
